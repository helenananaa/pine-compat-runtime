## 1. 目标、范围与既有计划的关系

目标：让更多真实现代策略能够执行，并能解释和验证其结果；在语义稳定后，
补齐被实际需求证明必要的账户能力，再基于测量优化性能。

五阶段依次为：

1. 冻结现代策略语料与分阶段测量基线。
2. 按语料根因补齐语言与内置函数阻塞。
3. 建立独立结果对照，修正策略执行偏差。
4. 按需求扩展账户、精度和报告能力。
5. 建立性能基线，逐项优化并验证资源边界。

本计划接续 [策略准确性执行计划](STRATEGY_ACCURACY_NEXT_EXECUTION_PLAN.md)：
旧计划 A/B/C 的混合 OCA、宿主中立 session 风险窗口和普通跨 bar 跳空已有收口记录；
Stage 18g OHLC 路径与 Stage 23 Bar Magnifier 也已有收口记录。
这些成果是本计划的回归基线，不重新作为待开发阶段。

旧阶段 D1 尚缺逐样本清单、去重与测量，本计划阶段 1 承接这些工作。
旧 D2 聚焦“已接受但执行错误”，本计划阶段 2 新增独立的语言阻塞补缺通道，
阶段 3 承接有独立预期结果的行为修复。不能因为阶段 3 缺参考结果，就停止阶段 1/2。
最新缺口依据见 [现代策略语料审计](STRATEGY_MODERN_CORPUS_BEHAVIOR_AUDIT.md)。

本仓库负责解析、语义分析、类型、历史、状态、确定性 broker 行为和宿主中立契约。
行情获取、交易所日历维护、用户系统、数据库、网络、调度、真实订单和
CandleScope 适配继续由宿主负责。核心的新增测试必须可以离线运行。

继续暂停 Pine v1-v4 策略兼容和大规模源版本扩张。新语法、函数、账户字段均按
最小可验证切片实施；执行本计划不自动意味着提交、推送、合并或发布。

## 2. 执行约定与依赖关系

### 2.1 状态与检查项

- `planned`：只有计划，尚未执行。
- `in-progress`：正在执行，已有过程记录。
- `partial`：有可用交付，但至少一项验收条件未满足。
- `blocked`：当前步骤有明确缺失输入；写明仍可继续的独立步骤。
- `closed`：本轮事先冻结的范围全部通过验收，证据可复现。
- `deferred`：有依据决定本轮不实施；不能计作能力已完成。

下文复选框只有在产物和证据已保存后才能勾选。阶段 2/3/4/5 可以多轮迭代，
每轮须有固定样本集和切片清单，不能以“修了一个功能”宣称整个语言或策略完整兼容。

### 2.2 依赖与可提前开展的工作

| 阶段 | 实施前置条件 | 可以提前进行 | 不满足条件时 |
| --- | --- | --- | --- |
| 1 语料基线 | 步骤 0 完成 | 来源盘点、工具接口设计 | 缺数据仍可测解析/语义分析，单列缺失项 |
| 2 语言补缺 | 阶段 1 已冻结清单与失败排名 | 查询规范、制作最小样本 | 未知语义保持拒绝；继续其他有证据根因 |
| 3 执行准确性 | 目标样本能运行，且有冻结输入和独立预期 | 收集参考输出、设计比较器 | 缺参考只暂停对应行为修复 |
| 4 账户与报告 | 需求来自语料，相关成交基础已验证 | 需求盘点、单位及契约设计 | 无明确需求则记录 deferred |
| 5 性能与资源 | 基准样本已稳定，相关正确性检查通过 | 早期保存测量基线、资源故障诊断 | 语义未稳定时暂缓优化结果验收 |

默认按 1→2→3→4→5 推进。若阶段 1 已发现有独立证据的错误成交，
该修复优先于新增语法；若参考样本已经能运行，阶段 3 不必等待所有语言缺口清零。
阶段 4 如果精度问题本身阻塞阶段 3，可先交付一个有证据的最小精度切片，再返回阶段 3。
阶段 4 无合格需求时，可以记录 deferred 后进入阶段 5；这不等于阶段 4 能力已实现。

### 1.5 生成五项独立指标

每个阶段记录 `passed / failed / missing_input / not_run / excluded` 及原因。
样本可出现解析通过、语义失败、运行未执行、无参考等组合，不能压成单一成功标记。

| 指标 | 通过含义 | 汇总要求 |
| --- | --- | --- |
| 解析 | 源码及所需依赖无解析错误 | 通过脚本数/N；缺源码另列 |
| 语义分析 | 无阻止执行的语义错误且可生成可执行表示 | 通过脚本数/N；另列解析通过后的条件比例 |
| 运行 | 指定输入完成执行且无目标运行错误 | 通过场景数/M；另列输入齐全且可执行场景上的条件比例 |
| 输出可比对性 | 输入设置对齐，独立参考存在且目标字段能无歧义映射 | 可比场景数/M；明确字段覆盖及比较器状态 |
| 结果一致性 | 预先声明的目标字段在固定规则下通过独立比较 | 一致场景数/可比场景数，同时展示参考覆盖率 |

分母为零时输出 `N/A`，不输出 100%。负向控制单列预期拒绝通过率。
一个场景只覆盖交易列表时，不能据此声称逐 bar 权益或 intrabar 路径也一致。
没有交易的运行成功样本标记 `no_trades`；没有覆盖目标行为时不能作为成交正确性证据。

- [x] 优先处理有证据的已接受错误，其次处理受影响脚本多、依赖少、语义明确的阻塞。

## 9. 每个行为切片的共同验收

### 9.1 验证顺序

1. 运行目标最小用例，确认失败根因及修复后断言；有效测试数不得为零。
2. 运行受影响模块的正向、边界和负向用例。
3. 验证该切片涉及的增量、实时和跨宿主行为。
4. 重跑固定目标语料与必要对照，解释新增通过、退步和输出变化。
5. 更新 fixture、golden、conformance、相关契约文档及切片 audit。
6. 执行 `git diff --check` 和 `scripts/verify.sh`，保存命令、退出码和有效测试数量。

常用定向命令按改动选择，不要求每次重复运行全部：

```bash
cargo test -p pine-syntax
cargo test -p pine-sema
cargo test -p pine-runtime --lib
cargo test -p pine-runtime --test incremental
cargo test -p pine-runtime --test realtime
cargo test -p pine-runtime --test session_windows
cargo test -p pine-runtime --test profile_fixtures
cargo test -p pine-cli
```

`check_host_parity.py` 验证覆盖登记，不能替代真实 Python/WASM 执行。
完整门禁包括 WASM/Node smoke 与新构建的隔离 Python wheel 测试。
新增测量器/比较器的确定性单测应接入门禁；私有语料全量运行和性能测量单独留证。

## 10. 阻塞处理与恢复步骤

| 情况 | 暂停的工作 | 可以继续 | 恢复条件 |
| --- | --- | --- | --- |

恢复时重新记录 HEAD、输入 hash、未完成步骤和目标用例；不要重做已经有有效证据的无关阶段。

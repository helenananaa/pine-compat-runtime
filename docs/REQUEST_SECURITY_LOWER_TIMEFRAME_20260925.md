# Historical lower-timeframe `request.security` (2026-09-25)

Pine v5/v6 `request.security()` accepts host-provided lower-timeframe bars in historical execution. The requested expression runs in the lower-timeframe context. Each chart bar receives the last intrabar by default, or the first intrabar with `lookahead=barmerge.lookahead_on`. An empty chart period forward-fills with `gaps_off` and returns `na` with `gaps_on`. Named `calc_bars_count` truncates the requested history before expression execution. This matches the historical first/last intrabar rule in TradingView's [Other timeframes and data](https://www.tradingview.com/pine-script-docs/concepts/other-timeframes-and-data/) documentation. The core consumes bars through its host-neutral request provider.

For forming or confirmed live chart updates, the host must push ordered intrabar updates through `RequestFeed`. The request evaluates only bars through the latest explicitly received intrabar in the current chart period; static provider rows from later times cannot become live values. Both lookahead modes then select the latest observed intrabar, as TradingView describes for realtime LTF requests. With no feed update in the current chart period, execution fails explicitly rather than reading future provider data. Unbounded requests reuse the existing incremental request evaluator when their expression is eligible; bounded requests replay their capped history. The runtime test covers a forming intrabar, its confirmation, a second forming intrabar, a chart confirmation, bounded and unbounded cumulative state, isolation of the earlier confirmed chart result, and rollback when a future-period intrabar arrives during the current preview. Native documentation warns that realtime LTF requests can repaint; a TradingView streaming-event numerical trace has not yet been compared.

The tracked `tests/fixtures/request/security_lower_timeframe.pine` and runtime tests cover v5/v6 lookahead selection, a chart period without intrabars, gap handling, and `calc_bars_count` state reset. In particular, a missing chart period carries forward the previous period's first intrabar under historical `lookahead_on`. A separate v1-v4 synthetic test verifies their versioned default: v1/v2 select the first intrabar and v3/v4 the last. The CLI run on ignored 1-minute chart / 30-second requested CSVs returned `[[2,4,6,6],[1,3,5,5],[2,4,6,null]]` with no diagnostics; input and output are retained under `.local/community-coverage-20260923/security-ltf-*`. The final locked seven-package test passed after the realtime change; its log is `.local/community-coverage-20260923/security-ltf-realtime-seven-package-tests-20260925.log`.

Native TradingView v6 check on COINBASE:BTCUSD daily chart compared two `request.security(..., "60", close)` plots against `request.security_lower_tf(..., "60", close)` array first/last plots. Three closed chart bars showed the same pairs on the corresponding plots: `(62950.71, 63018.75)`, `(78175.94, 77665.14)`, and `(76268.48, 76348.74)`. The same script compiled as Pine v5 and showed `(78175.94, 77665.14)` against the matching array values on one closed bar. This confirms the native historical first/last selection and script compilation in both versions; the repository's exact numeric parity was checked on synthetic host-provided bars, since the native hourly feed was not exported. Pine v1-v4 legacy `security()` has synthetic version-default coverage but is not claimed native-qualified by this check.

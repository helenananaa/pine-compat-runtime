# LazyBear Volume Flow Indicator v1 native check (2026-09-25)

The original open-source [Volume Flow Indicator [LazyBear]](https://www.tradingview.com/script/MhlDpfdS-Volume-Flow-Indicator-LazyBear/) has no version directive, so it runs as Pine v1. The source as shown in TradingView's source tab is copied, with blank lines omitted, to the ignored `.local/community-coverage-20260923/lazybear-volume-flow-original-v1-20260925.pine`. Analysis reports no diagnostics and no unsupported features. It exercises `iff`, `stdev`, `sma`, `sum`, `ema`, history references, volume, a user function, and four plot calls.

The native chart export `I:\sys\下载\COINBASE_BTCUSD, 1D (14).csv` was copied to ignored `lazybear-volume-flow-native-v1-20260925.csv`. The check uses 4,282 confirmed `COINBASE:BTCUSD` 1D bars, the script's default inputs, and the exported chart OHLCV in `lazybear-volume-flow-chart-bars-v1-20260925.csv`. The last, forming bar is excluded. Note that the chart export's `Volume` field has lower precision for many early bars than another export from the same chart. Using the VFI export's own volume field is necessary for this comparison.

The original local run initially left `vfi` and its EMA undefined for about 61 bars after native TradingView had begun plotting. A probe isolated the cause to `sum(vcp, length)`: the v1 native result collects `length` non-`na` inputs, while the runtime previously retained `na` samples in a fixed bar window. `math.sum` now keeps the latest `length` valid source values and retains its previous sum on an `na` input bar. Its state uses same-bar replacement and rollback support. Focused modern and explicit-v1 math tests cover the observed sparse-input behavior.

After the fix, running on the VFI chart export's current OHLCV yields **8 differences among 17,128 plot cells**. All four columns match on bars 0 through 4,277. The two computed lines differ on each of the final four confirmed bars (September 21–24, 2026), by at most about 0.0051. A fresh chart insertion and second export reproduced those values.

The remaining differences are explained by TradingView's changing historical volume. A separate, earlier TradingView chart export, `I:\sys\下载\COINBASE_BTCUSD, 1D (10).csv` (SHA-256 `740636A135737E81A29D591B0DCCB89F34687ED357ED0E17AD1F6DFA2ADE9156`), records volumes of `14086.87276351`, `8943.87588877`, `7856.10631934`, and `6840.72162128` for those four bars. The later VFI export contains `14122.3475358`, `8944.37757303`, `7856.10556163`, and `6840.72162124`, while its *plot values* still correspond to the earlier volumes. Replacing exactly these four volume inputs with the earlier exported values gives **zero differences across all 17,128 cells**. The prior export is copied to ignored `lazybear-volume-flow-prior-chart-snapshot-v1-20260925.csv`; `compare_vfi_v1_20260925.py` verifies each replacement's time, OHLC, and source volume before comparing both runs. This is a reconstructed matching input snapshot, not a claim that the later TradingView export's own OHLCV and plots are internally synchronized. The script's other symbols, intervals, inputs, and realtime forming bar remain unchecked.

On September 26, the unchanged original was rerun against that same 4,282-bar reconstructed snapshot in batch, incremental, and realtime-history modes. The three full JSON outputs are byte-identical, SHA-256 `2be97bf75c43236886d75354e4f63741a81cdeda91c8d436861da0929092eddd`, and structurally identical to the earlier zero-mismatch native-comparison output. Each contains four 4,282-position plots and zero diagnostics. This extends execution-mode consistency to the sparse-input `math.sum` path, but does not establish live forming-tick or unsynchronized-export parity. The three ignored outputs are `.local/continued-popular-20260926/vfi-v1-{batch,incremental,realtime-history}.json`.

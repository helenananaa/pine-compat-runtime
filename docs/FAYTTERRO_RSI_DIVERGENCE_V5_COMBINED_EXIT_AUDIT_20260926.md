## Source and broker boundary

The published source enters `Long` and `Short` with an explicit quantity and calls the respective exit in the same calculation. The limit and stop are absolute prices derived from the signal bar's close. `trail_price` is also that close; `trail_offset` is numerically `close * tsb` or `close * tss`, but Pine interprets this argument as **ticks**, so the broker must multiply by `syminfo.mintick`. No code should silently reinterpret the author's numeric expression as a percentage of price.

TradingView's [v5 strategy documentation](https://www.tradingview.com/pine-script-docs/v5/concepts/strategies/) establishes that one `strategy.exit` can produce multiple exit orders, `limit` plus `stop` creates a take-profit/stop-loss bracket, and when one exit from a call fills the others cancel. It also describes trailing activation, tick offsets, reservation and OCA reduction. The [v6 migration guide](https://www.tradingview.com/pine-script-docs/migration-guides/to-pine-version-6/) confirms that v5 gave absolute arguments priority over relative arguments for the same exit level. Those references do not themselves settle every historical-bar ordering and same-calculation attachment detail for this exact four-parameter v5 call. A native chart/trade export is still required before asserting fill parity.

Current code has four mutually exclusive `PendingExitTrigger` variants (`Stop`, `Limit`, `Bracket`, `Trailing`) in `crates/pine-runtime/src/strategy/broker/pending_exits.rs`. The analyzer rejects mixed fixed/trailing args in `crates/pine-sema/src/analyzer/strategy.rs`; `eval_strategy_exit` in `crates/pine-runtime/src/builtins/strategy.rs` also returns without placing an order if trailing and fixed arguments coexist. Merely removing either guard would incorrectly declare executable compatibility.

## Implementation acceptance contract

1. Represent all child exits from one call under **one** exit identity and reserved quantity. The fixed stop, fixed limit, and trailing stop compete for the same position slice; a child fill cancels its siblings. A pending entry with the matching `from_entry` must retain the attachment until the entry fills.
2. Give the trailing child its own inactive/active state, activation price and tick-converted offset. Activation or ratcheting alone must not record a fill or cancel the fixed children. A fixed child may fill before activation or afterward. Preserve existing gap, intrabar path, limit verification, slippage and long/short behavior.
3. Select the actual filled child before generating exit-specific `comment_*` and `alert_*` fields. A gap fill at the bar open must still retain which child triggered it; fill price alone cannot distinguish two stops or a stop and active trail. Keep OCA and reservation accounting at the parent exit level.
4. Test both long and short paths: fixed stop first, fixed limit first, trailing first, trailing activation followed by fixed exit, gap through fixed stop/limit, two triggers in one OHLC bar, same-calculation pending-entry attachment, replacement under the same ID, and competing partial reservations. Compare a minimal native four-parameter probe before admitting the original full script.
5. After broker tests pass, analyze the unchanged original, run it on a frozen full-history chart input, and compare native plot and trade exports using the exact chart symbol, timeframe, input values, price grid and confirmed-bar cutoff. A successful analysis alone is not native parity.

# Donchian breakout revision: exploratory source audit (2026-09-26)

The public [Donchian Breakout Strategy by millerrh](https://www.tradingview.com/script/hyYvFjux-Donchian-Breakout-Strategy/) is a popular open-source Pine v5 strategy. Its current TradingView source and native exports have **not** been retrieved. A [GitHub mirror of a third-party revision](https://github.com/hasnocool/tradingview-pine-scripts/blob/main/Donchian%20Breakout%20no%20repaint.pine) explicitly calls itself "Donchian Breakout no repaint", credits `@millerrh`, and identifies `dhafinskii` as the reviser. It must not be treated as millerrh's unchanged publication or counted as native compatibility.

The mirrored GitHub page text is retained as ignored `.local/continued-popular-20260926/donchian-breakout-revision-mirror.pine` (SHA-256 `53bb4ac8d490d1894b230628c1bf4855665ef2cf06deb0b9181b85330b50e904d`). Its embedded 151-line Pine section was extracted into ignored `donchian-breakout-revision-extracted.pine` (SHA-256 `eef0846ffab15252af9d559c45e02eba1f025388a05d1993e51bc23df001e5b5`), replacing nonbreaking spaces in the page copy with ordinary spaces. The extraction changes typography and is a diagnostic derivative, not a source-authenticity claim.

`pine-compat analyze ... --format json` on that extraction produces one `E_UNSUPPORTED_FEATURE` at line 89, with zero other diagnostics. The line calls `request.security(syminfo.tickerid, tfSetSlope, ta.rising(maSlope, 1), barmerge.gaps_off, barmerge.lookahead_on)` after `maSlope` was itself assigned from another `request.security` call. The requested expression captures a chart-level series returned by a separate request callsite, which the current host-neutral runtime explicitly rejects. The resulting `executable=false` is a truthful boundary; the analyzer does not silently replace the captured series or omit the filter. The derivative's default `useMaFilterSlope=true` means this path matters to its trade signals. No interpreter change is justified without a native oracle for the exact context/capture behavior.

[TradingView's Pine v5 request documentation](https://www.tradingview.com/pine-script-docs/v5/concepts/other-timeframes-and-data/#nested-requests) now narrows the required semantics: without `dynamic_requests=true`, a dependent outer request does not rerun the inner request in its own context; it receives the inner request's already calculated value. The revision declares Pine v5 and does not enable dynamic requests. The documented direct-alias example establishes this boundary, but does not provide an oracle for the revision's `ta.rising(maSlope, 1)` expression or its higher-timeframe merge. A fix must distinguish this non-dynamic value capture from v5 explicit dynamic and v6 default-dynamic nested evaluation; simply allowing the rejected expression would produce an unsupported parity claim.

The next qualification step is to retrieve millerrh's unchanged current source through the TradingView Chrome source panel, check whether it contains the same cross-request series capture, then collect chart and trade exports on a fixed symbol/timeframe. The Chrome extension's `tabs.list()` call timed out again on September 26, so neither original-source admission nor native parity is claimed here.
